Getting your repo found and correctly listed

Everything below is what Klondike's own discovery script actually checks - not guesses about how a "skill store" might work in general, but the literal signals this crawler looks for, found by inspecting real repos that were missing or misclassified.

1. Get discovered at all

Klondike finds candidates via three signals, unioned:

  • A skill.json file (anywhere, but locale/en-us/skill.json is checked first) containing a pip_spec field.
  • The GitHub topic ovos or openvoiceos set on the repo.
  • ovos appearing literally in the repo's own name.

The single biggest lever if your repo isn't showing up at all: add the ovos or openvoiceos GitHub topic. Several real, actively-maintained repos (including some of OVOS's own) were invisible to this store simply because they had zero topics set and aren't skills, so no skill.json existed either.

2. Get classified correctly

Component type is derived from formal declarations, not guessed from a description:

  • Skill - has a skill.json.
  • Plugin (OCP, TTS, STT, PHAL, Pipeline, Persona, Solver, ...) - has a namespaced entry-point group declared in setup.py or pyproject.toml, e.g. entry_points={"opm.pipeline": "..."}. This is the same mechanism ovos-plugin-manager itself uses at runtime, so it's the most reliable signal - and a repo can have both a skill.json and a plugin entry-point at once (they aren't mutually exclusive); the entry-point takes priority for classification when both are present.
  • Tool - no skill.json, no entry-points, but setup.py/pyproject.toml declares a real installable package (a name= field) - catches CLI clients and helper libraries.

3. Get your PyPI status verified

skill.json doesn't require a package_name field, but without one Klondike can't confirm PyPI status even when the package genuinely is published. Resolution order:

  1. skill.json's own package_name field - most reliable, set this if you can.
  2. setup.py/pyproject.toml's own name= declaration.
  3. The repo's bare name, as a last resort - works only when it happens to match the actual PyPI package name.

4. Reach "Looks Complete"

Either of these gets you there:

  • A confirmed manifest (from step 2) and published on PyPI and a real GitHub release.
  • Already listed in OVOS's own upcoming Skill Store (not yet officially launched) - a maintainer reviewing and merging a submission there counts as a stronger signal on its own, since that store doesn't require PyPI or a release either.

Missing PyPI or a release doesn't exclude you - it shows as an "Incomplete" badge with the specific gap named, not a rejection.

5. Other things Klondike picks up automatically

  • A LICENSE file - detected by GitHub itself, not read from skill.json. Missing one shows an explicit warning on the detail page.
  • A real README - used as a description fallback when neither skill.json nor GitHub's own repo description have one, and scanned for Install/Setup/Configuration headings to surface any repo-specific setup steps beyond a plain pip install.
  • A locale/<lang>/ folder (Skills only) - each subfolder becomes a language flag on your listing.
  • Being tracked by OVOS Localize - gets you a "Translate" link automatically; nothing to add on your end beyond being in their own list.

Forks

Forks are excluded by default (to avoid random personal test-forks), except for a short list of orgs already confirmed as genuine first-party parts of the OVOS ecosystem (OpenVoiceOS, NeonGeckoCom, OscillateLabsLLC, TigreGotico, JarbasHiveMind, smartgic). If your org publishes real, maintained forks and isn't on that list, ask and it can be added.

How often does it refresh?

New repos get picked up within a few runs of appearing (the crawler runs every 3 hours). Already-known repos refresh on a rotation, not every run - so a change you make today may take a few days to show up, not a few hours. If you need a specific repo re-checked sooner, open an issue.
